# 队列采集器

采集器（`meterbook.collection`）主动从来源协议的投递队列拉取用量事件，把三个阶段分别可靠落盘，
任一阶段断线都能从本地状态恢复，不会多记一份有效用量。

## 三个持久化阶段

1. 拿到投递（capture）：`queue_deliveries` 保存正文与摘要，`collection_attempts`
   保存每次投递的 `receipt_handle`、到期逻辑秒与续租次数。同一 `delivery_id` 再投递会换
   handle，旧 attempt 标记为 superseded/lost，旧 handle 永远不会被用于确认。
2. 业务接收（accept）：调用既有的 `receiver.receive`，事件先可靠写入 `events` 表，
   delivery 回链 `event_id`。重复事件以 duplicate 记录，不产生第二份有效用量。
   report/correct/cancel 的合同、双边序列与 revision 约束完全不变；等待前序只发生在
   `event.drain`，此时投递已经可靠接收并可确认，不会无限占用租约。
3. 向供应商确认（acknowledge）：只有正文与业务结果都已落盘后才调用 `/ack`；
   成功后 delivery 进入 acknowledged。确认响应丢失时本地保留 ack_pending，
   下一次 run 先补发确认，退出摘要列出仍待补发的 delivery。

## 租约

队列返回逻辑秒 `now` 与每个 handle 的 `expires_at`。采集器用最新已知队列时钟
`sweep` 到期租约：到期后不再假定仍持有投递，attempt 记为 lost、delivery 回到
lease_lost 等待重新投递。处理临近到期（`renew_threshold` 逻辑秒内）时按约定调用
`/renew`，续租次数受 `renew_limit` 约束；409 一律视为失租。

## 坏信封与冲突

- 不合法或业务无法接收的信封进入 `quarantined_envelopes`，可查询、可审计，绝不静默丢弃。
  是否自动确认由操作员配置 `quarantine_ack` 决定；默认关闭，需 `resolve_quarantine`
  显式 ack（不产生用量）或 retry（修正后重跑业务接收）。
- 同一 `delivery_id` 换正文：保留冲突，delivery 进入 conflict，两个版本都不自动确认。

## 运行控制

`Collector.run(source, limit, max_attempts, max_messages, deadline, monotonic)`
单次运行受条数、远程调用尝试与时间预算约束；`pause`/`resume` 可暂停与恢复，
`status`、`list_deliveries`、`list_quarantine`、`runs` 用于查询。运行结束返回
`pending_acknowledgements`，说明哪些确认尚待补发。

CLI：

    python3 -m meterbook --database ledger.sqlite collect run --source http://127.0.0.1:8765
    python3 -m meterbook --database ledger.sqlite collect pause|resume|status
    python3 -m meterbook --database ledger.sqlite collect deliveries|quarantine|runs
    python3 -m meterbook --database ledger.sqlite collect configure --quarantine-ack

测试在本地队列（`tests/collection/fakequeue.py` 与回环 HTTP 服务）上演练续租、失租、
重复投递、两个消费者争抢以及落盘后断线。冻结账单的发票摘要不受采集重试影响。
